If the host stops, the pod keeps billing until the next host's `recover()` releases it with reason `restart` (`worker_owner.py:217-231`, `adapter.py:291`). If the computer sleeps, release happens late, after it wakes (`worker_owner.py:201`).
- **Journal fields:** `hourly_usd`, `estimated_cost_usd`, `accounted_at`, `paid_expires_at`, `idle_expires_at` (`worker_owner.py:313-318,351`). `lease_row` shows `idle_expires_at` only while idle and hides the paid expiry (`machine.py:939`). Its cost is accrued only on reuse or release (`worker_owner.py:315-318,482-484`), so the shown cost is stale.
- **No extension exists, by design:** host operations are setup, ls, status and release (`adapter.py:144-160,415-419`); a machine id is accepted only for release (`sdk/generation.py:312-315`). Reuse refuses "existing claim lifetime cannot be extended by reuse" (`target_selection.py:472-477`) and replayed consent (`:478-480`); `packs/runpod/docs/SKILL.md:39-41`; tests `tests/packs/runpod/test_target_selection.py:504`, `tests/packs/runpod/test_warm_session.py:146,325,727`.

**Approach:** compared (a) all three as asked, with `--until-release` unbounded; (b) the display and `keep --for`, with `--until-release` as "keep up to the cap" (idle release off, expiry set by the cap); (c) the display only. Chose (b): (a) cannot be made safe, because the only enforcement is a timer in the host, which a crash or sleep stops; (c) does not give Hannah a way to keep a machine. (b) needs no new journal schema and no daemon: it reuses `lease_row`, `PaidRunConsent.validate`, the owner's `_arm` and the release task path, and drops the idle-only filter in `lease_row`.

**Challenge:** Reviewed — a read-only critic delegated by the orchestrator in https://claude.ai/code/session_011EzfVz8zzHLnUqSqMnGUCT, 10 Nov 2026, because money and paid consent are involved. It traced the code above and recommended (b). Accepted:
- the keep operation lives on the owner, under its lock, needs the exact pod, a claimed record, an `idle` or `active` lease and the owner's current epoch, and refuses while a release is in flight;
- fresh consent goes through the existing `validate()` at the recorded rate and offer digest;
- cost is accrued to now before the new limit is written;
- keep must refuse when the host has no live owner: building a new owner there would run `recover()` and release the very pod the user wants to keep;
- the reuse rule is unchanged, and `SKILL.md` gains one sentence on keep.

Rejected: an uncapped keep; a pod-side cap (it would need a credential on the pod).

**Proof and limits:** CPU fakes through the real CLI and host operation, listed in [plan.md](plan.md#completion). No real pod is kept here; Plan 34 can check it live.

## Owner decisions

- **D1.** `--until-release` always needs `--max-usd`. It turns off idle release; the machine is released at the cap's expiry or on `astrid machines release`. No uncapped option. (Hannah agreed to the capped proposal, 10 Nov.)
- **D2.** Release needs a running host. `keep` refuses when no host owns the machine, and the CLI says that release happens only while a host is running. (A consequence of D1 and the current design; the provider-side cap is deferred.)
- **D3.** Ships with release 13, after Plan 32 lands on Agent `main` (Hannah put Plan 32 in release 13, 10 Nov).
- **D5.** A per-job GPU choice (`--gpu`) was requested by Hannah on 10 Nov ("we should be able to specify the specific GPU that we want"). Research found `astrid generate` never had one; the GPU flag people remember was in the Blender pack's deploy tool, removed with that pack's move out of the repo (5d841e305, 5 Nov), and `runpod.provision`/`runpod.session` still take `--gpu-type`. The SDK's `PlacementPolicy.gpu_types` override (cef4da11e, 1ae020677) exists but the CLI can't reach it. Decision (orchestrator, reversible): `--gpu` REPLACES the saved GPU list for that job, matching the existing policy semantics, rather than narrowing it. An explicit per-job `--datacenter <id>` similarly narrows only that job and never changes saved preferences; a selected network volume fixes its datacenter, so a conflicting override refuses.
- **D6.** Hannah, 10 Nov: "we should just keep on retrying until we get the pod". Generation waits for capacity instead of failing on the first out-of-stock quote, within a wait limit, with no pod and no spend while it waits.
- **D7.** Hannah, 10 Nov: "I think we should always just wait for capacity", retrying "every few seconds" until the preferred GPU on the preferred storage is claimed. Decision (orchestrator, reversible): one shared wait loop in RunPod target selection for `generate` and `machines claim`; retry every 5 s with jitter and rate-limit backoff; wait until claimed or cancelled by default, with `--capacity-timeout` and `--no-wait-for-capacity`. The user GPU order is authoritative; price breaks ties within one GPU. A definite rejection advances to the next allowed GPU/datacenter option, then reobserves and repeats. With no saved volume or explicit datacenter, use every datacenter returned by the provider; add no Astrid-invented geography filter. Prior art (four read-only explorers and the advisor, 10 Nov): the lifecycle library's `launch_when_available` (7e9f3817fbebeb74e41d14b81c09844a42988908) and the agent's journaled create loop in `acquire_target` (d6b5e01142f1c3349c44644cf0f13f49cd52658d) already retry definite capacity rejections, but `consented_offer` (`target_selection.py:364-408`) observes the offer once and fails with `stock_unavailable` before that loop, and the loop allows only 10 creates with backoff inside the remaining paid lifetime (`target_selection.py:537-539`; `worker_preparation.py:1302-1312,1397`). Nothing was deleted. Waiting without a quote needs a separate policy consent (GPU list, saved storage, hourly ceiling, cap), and the paid clock moves to a pre-POST stamp, so T6 is S.
- **D8.** Hannah, 10 Nov: preferences say "we want this GPU on this storage", and Astrid should prompt to set them when missing. The existing home is right: per-user `machines.runpod` in the Runtime's generation settings document (`/v1/app-state/user/generation`, `astrid/core/generation/settings.py`), already holding ordered `gpu_types`, `volume` and `datacenter_id`, defined at `target_selection.py:122-215`. It is written by the `runpod.setup` action (`worker_owner.py:233`), `generate targets --save` (`astrid/sdk/generation.py:958-983`) and the JSON settings checkout and checkin; there is no guided setup and no App preference screen. Decision (orchestrator, reversible): add `astrid machines setup`, which wraps `runpod.setup`; the prompt records an optional datacenter with default any, while a selected volume fixes the datacenter.
- **D9.** Hannah, 10 Nov: "manual commands to claim these as well". Decision (orchestrator, reversible): `astrid machines claim` enters the same custody journal and retained-host lease as `generate`, so a later job reuses the machine warm; it is not a separate pool and not the older `runpod.provision` handle. Its `--datacenter` override narrows only that claim and is bound into its consent.
- **D10.** Orchestrator correction, 10 Nov: preferences record the nonempty ordered GPU choices, storage volume and optional datacenter; setup defaults to any datacenter, while a volume pins its datacenter. Per-job `--gpu` and `--datacenter` narrow only that job/claim. Try GPU choices in the user's order. Within one GPU type, try the cheapest allowed datacenter first; datacenter is the open choice by default unless the user or volume fixes it. After a definite capacity rejection, advance to the next `(GPU, datacenter)` pair in that order, then reobserve. There is no global-cheapest ordering unless an existing internal path already provides it. Add no default geographic filters or provider allowlists.
- **D11.** Orchestrator decision, 10 Nov: `machines setup` fills an unsaved image with the Plan 34 live-validated RunPod worker image `runpod/base@sha256:820c605eaaa276de20a0d77993fb0846d54e180efff5de67d46341ed399b5a7f` (Plan 34 live validation, 10 Nov 2026; astrid-dev PR #260). It preserves a saved image, and optional `--image <name@sha256:…>` overrides it for setup. The account identity always comes from the saved credential reference; the key is used in memory only to authenticate read-only setup lookups, never as identity, stored, shown, logged, or included in errors. Keep the generic compute default unchanged.
- **D4.** One review round at the end, S route: the plan changes paid consent. No review stop: T2 and T6 are the load-bearing tasks; T6–T8 were critiqued by the advisor (Codex Astra, 10 Nov) before implementation. Accepted: a separate policy consent for stockless waiting; a durable pre-POST paid clock; cancellation and single-POST requirements; claim's one consent covers its initial retention; refusal, not a second pod, for a different GPU while held; T8 as S; one wording pass (T4). Deferred: restart-resume of a wait, volume metadata caching, a per-job `--volume`, and launching setup automatically. The final review covers T2 and T6–T8.

- **D12.** Hannah, 10 Nov: "Why would a pod release when a job fails? ... if we said we have a budget or a time limit, then we should just respect that. We shouldn't kill a pod when a job fails." A failed job keeps the machine idle within the consented idle and paid limits; immediate release only when reuse would be unsafe or unknown. Found by Plan 34 (Terra trace): `machine_run.py:70-102` releases unconditionally in `finally`, `machine.py:820-844` releases failures and `machine.py:574-582` releases failed claim preparation, so a failed job could never be diagnosed or retried on the same pod. Task T9 (S), with its own focused review because the plan's single review round (D4) came before it.

- **D13.** Hannah, 12 Nov, after a live failed job deleted a kept pod (`unsafe_job_state`): "unless the actual machine fails for some kind of terminal reason, we should never automatically terminate it, because people have set up the rule to keep the pod warm." This narrows D12's immediate-release list. A preparation or installation that cannot be verified no longer releases the machine when the pod is reachable, exactly owned and its jobs are verified stopped: it is kept as `stale_after_failure` within the consented idle and paid limits, generation is refused on it, and the next claim re-prepares it on the same pod. A refreshed install receipt (only `receipt_sha256` changed) is accepted. Immediate release stays for custody lost or changed, an unverifiable job stop, an output digest mismatch, the paid limit, an unreachable engine, a reset failure and host shutdown (D12; restart retention needs the deferred pod-side cap below). Each release records its own reason in place of `unsafe_job_state`. Implemented on Agent `r13/keep-warm` for Release 13 (decision log, 12 Nov).

## Deferred

- A session-level keep: hold a machine across jobs and tools from one setting, with extend and release.
- Better default output: `generate` writes to `./outputs/<task-id>/` under the current folder, named by the workflow. A per-project folder and readable names are a separate follow-up.
- A provider-side or pod-side cap that holds when no host runs.
- `runpod-lifecycle` `availability._query` (f294881, `availability.py:58-68`) drops the HTTP `Retry-After` header on 429; expose it as a typed field so Astrid can honour it. For this plan, Agent honours typed retry metadata when supplied and uses bounded exponential backoff when the pinned client cannot provide it.
